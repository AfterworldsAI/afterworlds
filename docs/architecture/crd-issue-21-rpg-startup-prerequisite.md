## Outcome and ownership

A fresh RPG story can establish its world, create or submit a character, confirm play configuration, and enter ordinary play through the built application. No test-only character seeding is involved.

CRD Issue 15's RPG setup/orchestration boundary owns phase progression; the CRD Issue 2b character service owns persistent mechanical state and binding; Rules Package authority owns mechanical identities; existing entitlement and provider services own access and settlement. CRD Issue 19 supplies thin API/UI surfaces. This work requires acceptance as a prerequisite extension beyond CRD Issue 21's narrow wiring allowance.

## Proposed product contract

1. **World first.** Start in `SETUP/world_setup`. The GM reads the Sojourner's world summary, confirms its understanding briefly and asks about critical omissions. Show an explicit **Confirm world** action against a server-recorded, typed confirmation target identifying the delivered setup Turn and world-summary/canon revision; never infer confirmation readiness from prose. This advances only to character creation. World edits invalidate an outstanding confirmation. Keep approved Story Bible service paths; a confirmation never bypasses canon validation. Move the existing configuration-first UI behind this sequence.

2. **Select supported rules.** On entering character creation, show the supported, enabled, published Rules Packages available through current runtime authority, including system/version. Persist the Sojourner's explicit package selection; if only one exists, show it for confirmation. The server resolves its UUID and exact effective binding. No hardcoded fixture package, model-selected authority, source-text fallback, package publication or activation. Missing, stale, quarantined or unsupported authority blocks acceptance with a recoverable explanation.

3. **Two character paths, one gate.** Offer conversational GM-led creation and pasted completed-sheet entry. The former gathers class, background, stat-generation method, equipment and backstory hooks through conversation; the latter acknowledges the submission and asks about missing or ambiguous data. Both produce the same reviewable typed candidate. A form may support correction but cannot replace the conversational path. Never silently invent missing numbers, choices or grants. If a requested generation method has no supported code-owned operation, request supplied results or a supported method; do not fabricate rolls or add a new dice subsystem.

4. **Make the candidate explicit.** Extend the existing RPG setup Writer output with a versioned envelope containing visible GM text and a phase-specific world-confirmation proposal, character proposal or clarification result. Code validates proposals and owns confirmation targets and phase transitions. This is a bounded Writer contract extension, not an additional provider pass or an alternate narrative pipeline. Character proposals use the existing ruleset-specific schema and authority identities; unresolved fields stay visibly unresolved. Persist pending proposals and their revision/binding in typed, versioned metadata on the existing setup Node, separate from the accepted character. Show the Sojourner a readable sheet, outstanding problems and **Accept character**. Chat prose is never the authoritative sheet; model-proposed identities and values are untrusted inputs to code validation.

5. **Accept through the owner.** Accept character validates the displayed candidate, expected revision and current exact binding, then uses the existing character-state service to create/update the first-class sheet. Require both validity and readiness, including the Rules System Adapter's adjudicability check. Successful acceptance and advancement to `play_configuration` commit atomically. Missing/ambiguous inputs require clarification without advancement. Readiness means complete, well-formed recorded inputs for the binding; it does not certify every build choice as legal or every mechanic as executable. Existing CRD Issue 15c restrictions remain authoritative.

6. **Confirm configuration and start.** After character acceptance, the GM summarizes session type, tone, dice handling, GM cheating, house rules and content boundaries for confirmation, using existing defaults and typed configuration. GM cheating remains on by default; it never changes recorded numeric roll results. Unsupported house-rule mechanics cannot acquire authority from free text. An explicit **Complete setup** action rechecks the accepted character and binding, saves the displayed confirmed configuration, and atomically sets `setup_phase=complete` and `play_status=IN_PLAY`. It generates no playable scene or fabricated player action. The next ordinary Sojourner interaction follows the existing RPG adjudication/narrative path. The final setup confirmation remains setup-only and does not count toward Rolling Summary.

## Persistence, failure and access

Reload restores the authoritative phase, selected package, pending candidate/problems, accepted sheet and configuration. Use existing persistence carriers with narrow typed/versioned extensions; new tables or migrations require a reviewed dependency. Accepted mechanical state stays in the character service, not session fields or Story Bible. Revising an unaccepted proposal is supported; this prerequisite does not add an in-play rebuild/rebinding workflow.

Phase confirmations are typed operations against the displayed revision and existing story serialization boundary. Stale, repeated, concurrent or out-of-order requests cannot overwrite newer state, skip prerequisites, duplicate acceptance or invoke/pay a provider twice. A repeated completed confirmation returns current state. Validation, authority or commit failure leaves the previous committed phase/sheet intact and permits correction/retry.

Provider-backed setup exchanges use production hosted/BYOK readiness, binding and bounded same-path fallback. Preserve intent-before-context, one stable prefix, existing core pipeline and applicable Safety/Contradiction gates. Visible GM text and its pending proposal commit together; failed/refused/blocked exchanges expose no candidate and retain existing non-billable failure/audit behavior. Successful delivered setup exchanges settle under existing rules; BYOK never deducts hosted credits. Pure confirmation mutations make no provider call or charge. Setup exchanges and confirmation operations remain excluded from narrative summary eligibility; later ordinary delivered RPG narrative counts normally. Hidden adjudication state must not enter setup presentation or summary source material.
