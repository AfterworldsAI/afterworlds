## Findings

1. **P1 — One earned ability increase can execute repeatedly under different choice IDs.** `src/afterworlds/pipeline/rpg/grants.py:334–357,367–382,391–419` validates each `(record, component, choice_id)` group independently. `_require_held` proves possession of the background or feat but does not bind the groups to the number of earned increase instances. Static admitted example: a level-1 Acolyte with Intelligence 10 records two distinct, structurally valid ChoiceRecords under `character_origins.acolyte/ability_scores`; each supplies +2 Intelligence and +1 Wisdom. Both groups satisfy the accepted `[2,1]` background rule and held-origin check, so `ability_score(INT)` returns 14 instead of refusing the second use of the single background increase. The same mechanism reuses one valid ASI feat selection for multiple `[2]` groups. CRD Issue 2b only checks that cited choice IDs exist and their individual schemas/identities are valid (`models/dnd5e_state.py:728–737`, `services/dnd5e_state/validation.py:219–241`); it does not prevent this. Required correction: bind contributing increase groups to actually earned selections and enforce source cardinality across groups before numeric use. Classification: merge-blocking entitlement defect; in-scope implementation, no new Owner semantics.

2. **P1 — Class feat choices reject their accepted qualifying-feat alternative.** `_check_feat_source` at `grants.py:237–244` admits only `named_feat` or a category choice when `named_feat is None`; it never consumes `or_any_feat_whose_prerequisites_are_met`. The exact native `classes.fighter.ability_score_improvement/ability_score_improvement` fact names ASI and also explicitly permits any qualifying feat, once per gain. Static example: Fighter 4 takes Skilled from that feature and uses a valid Skilled skill grant. `_feat_entitled` calls `_check_feat_source`, which refuses the feat despite the accepted alternative and attained class level. This is an admitted contributing proficiency path, not general feat execution. Required correction: execute the typed alternative with its prerequisite and per-gain validation; retain refusal where eligibility truly cannot be certified. Classification: merge-blocking supported-path defect; in-scope implementation.

3. **P1 — Skilled's shared skill/tool choice is split into an incomplete skill-only allowance.** The native `feats.skilled/skilled` fact is `SkillProficiencyChoiceFact(count=3, or_tools=any_tool_entry, repeatable=True)`. At `grants.py:562–564`, counts include only plain skill grants; tool grants spending the same choice are invisible. Static admitted example: one Skilled feat earned by Human Versatile, with three skill grants and one valid tool grant from that feat. A check using one of those skills receives proficiency despite four picks consuming the single three-pick allowance. Conversely, `_tool_grant_count` (`:659–685`) has no `SkillProficiencyChoiceFact.or_tools` branch and calls a legitimate Skilled tool selection missing authority. Required correction: validate the contributing shared choice across both grant collections and admit its typed tool branch, preserving earned-instance limits. Classification: merge-blocking shared-choice entitlement/supported-path defect; in-scope implementation.
