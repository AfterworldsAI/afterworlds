## Concrete implementation residues

1. **P1 — repeatability is not checked before counting earned feat instances.** `_feat_entitled` (`grants.py:236–285`) validates source/prerequisites but never repeatability; `_instances` (`:387–397`) counts every matching FeatSelection. A Wizard 8, base Strength 14, can record Grappler from each of its two earned ASI gains, with distinct, correctly linked +1 Strength choice groups. Source cardinality permits two total feat selections, both Grappler prerequisites pass, `_bind_to_earned` assigns two owners, and both increases execute: Strength 16 rather than refusing the second Grappler. `feats.md:17` permits a feat only once unless its Repeatable subsection says otherwise; Grappler has none (`:69–81`). This is contributing numerical entitlement, not a general build audit.

   **Authority gap:** the accepted `feats.feat_descriptions/repeatable` component is prose-bound with no facts. Grappler's typed AbilityIncreaseChoice has `repeatable=null`, not an explicit once-only rule. ASI and Skilled do carry typed `repeatable=true` in their grant facts. Preserve those exceptions; do not equate null with either repeatable permission or an accepted universal default without a source-backed contract. Minimum remedy: a coherent accepted default/exception authority (or explicit bounded per-feat policy) plus validation across the contributing feat's earned sources. C6 presently adds neither.

2. **P1 — an explicitly linked feat choice can name a different feat.** `_check_feat_source` (`:295–342`) does not resolve `selection.source.choice_id` for its direct-fact ASI sources. Example: Wizard 4 has a source ChoiceRecord under `classes.wizard.ability_score_improvement/ability_score_improvement` selecting `RecordChoice('feats.grappler')`, but its FeatSelection is `feats.ability_score_improvement` citing that choice. A separate correctly linked ASI ability choice supplies +2 Strength. The validator admits the named ASI and executes its increase even though the source choice selected Grappler. Reusing `_linked` only for ability/skill/tool grants did not close this parent feat-selection seam. Required behavior: an explicitly linked feat source and selected record must agree before the feat can contribute.

   These examples do not depend on bypassing Pydantic with `model_copy`: the state model permits repeated FeatSelections, requires cited choice IDs merely to exist, and checks class/history totals (`models/dnd5e_state.py:727–805`). CRD Issue 2b validates each choice's own source/schema/identities and each feat's record/source existence, not cross-link agreement or repeatability (`services/dnd5e_state/validation.py:219–241,387–390`). Distinct correct schemas, valid RecordChoice identities and valid class totals satisfy those stored contracts.

3. **P1 — the Epic Boon alternative incorrectly inherits the primary category restriction.** `_check_feat_source:302–314` gates `or_any_feat_whose_prerequisites_are_met` with `in_category`. The accepted native Wizard Epic Boon fact says category `epic_boon` **or any qualifying feat**, with one gain at Wizard 19 (`classes.md:10216`). An eligible Wizard 19 selecting ordinary ASI through that feature is refused because ASI's category is `general`. The existing typed OR alternative already decides this; no new fact or Owner policy is needed. C6 README's Epic Boon “already safe” assessment is too broad.
